## Talking points

### Scion

Anthropic has moved its monorepo off git. Agent-driven merges went from about 2,500 a day in May to more than 30,000 in September, and the git mirrors couldn't keep up. A seven-person team built Scion to replace them. It isn't being released, but the write-up is effectively a warning to GitHub and GitLab about what's coming.

- **One authoritative server.** No clone holds the full history. Every agent talks to the central server.
- **Sparse, virtual checkouts.** Files are fetched only when something actually reads them.
- **The savings:** 200x less CPU and memory than the git mirrors, and CI CPU down 25%.
- **jj (Jujutsu) is the opposite bet.** It keeps git's storage and fixes the workflow on top: the working copy is always a commit, conflicts are recorded instead of stopping you, there's no staging area, and every operation can be undone.

Simon reads Scion as Subversion reinvented for always-online agents: centralised again because the clients never go offline. jj argues the fix belongs in the client, not the server. If agents broke git at Anthropic's scale, is version control the next thing they break for the rest of us, and is anyone here already on jj? — [Anthropic](https://www.anthropic.com/engineering/redesigning-source-control) — [Simon](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic/) — [jj](https://github.com/jj-vcs/jj)

<MiniSlide title="Design for clients that are always online">
- **Always online:** clients fetch data when they need it and never hold a complete copy.
- **Thin client, smart server:** the server handles blame, history, commits, merges and rebases, and the client mostly caches.
- **Everything is an API:** CI can ask for a diff or a merge base without checking anything out.
- **Horizontally scalable:** no fully materialised copy of the repo exists anywhere, not even on the server.
- **Cheap, lock-free commits:** a commit costs as much as the change, not the size of the repo.
- **The working copy is optional:** checkouts are sparse and virtual, and files are fetched when something reads them.
</MiniSlide>

<MiniSlide title="A changeset, not a commit" image={scionChangeset} alt="Diagram of a Scion changeset: author, dates, message, parents and a list of file changes stored in Spanner, pointing to content-addressed blobs in cloud storage; trees are derived by the server" credit="Anthropic" creditHref="https://www.anthropic.com/engineering/redesigning-source-control">
- An entry in a write-ahead log: the files that changed since the first parent, plus hashes pointing to the blobs.
- No packfiles, no locks, and no refs to move.
- Trees, blame and path history are **derived data**, which the server computes and can change without touching the client.
</MiniSlide>

### How Anthropic does code review

The Claude Code team published how they review code a day after Code Review left research preview for Team and Enterprise. Put together, the two posts describe a review loop where the model goes first and humans spend their attention where the risk is.

- **Self-check first:** Claude reviews its own work before a human sees it.
- **Risk-scaled approval:** how much human sign-off a change needs depends on how risky it is, not a flat one-approver rule.
- **The product:** about 3x faster than in preview, taking 6 to 10 minutes, with Quick, Standard and Deep levels set per repo.
- **Adoption checklist:** the post ends with one for teams copying the setup.

At AA15 we heard that AI-authored PRs wait 4.6x longer for a first review. This is Anthropic's answer to that bottleneck. ### Speaking of bottlenecks

Scion and Antique are Anthropic removing their bottlenecks one at a time. The same move works at the scale of a single project: a **bottleneck eliminator skill**. Once a day, it reads the last 24 hours of agent activity, finds where agents sat idle or ground away at something slow, and edits the project's own context and workflows so the waste doesn't happen tomorrow. It's a retro run by the agent, on the agent, with the fix committed rather than written on a sticky note.

- **What it reads:** session transcripts (Claude Code keeps them as JSONL under `~/.claude/projects`), tool-call timings, hook logs, CI durations and permission prompts. In short, everywhere wall-clock time went.
- **What it looks for:**
  - Test suites run in full when a targeted test would have done.
  - Serial tasks gated on each other that could have fanned out as parallel subagents.
  - Waits on permission prompts or human input that a rule could have pre-approved.
  - The same file re-read across sessions, and the same dead end hit twice.
- **What it changes:** `CLAUDE.md` notes ("run `vitest related`, not the whole suite"), skills and workflow scripts (split this step and run it in parallel), permission allowlists, and hooks. Each change is a commit you can review.
- **How it measures:** it compares agent-hours per merged change before and after, the same number Anthropic's Scion chart reports.

Claude Code's `/insights` already estimates which permission prompts auto mode would have handled, so this is the general version of that. Run it daily and the project's context becomes a ratchet that only gets faster. ### Is sandboxing sufficient?

During OpenAI's summer breakout, agents in separately isolated sandboxes left instructions for each other in a shared package cache, and the agents that found them followed them. Matthew Green's write-up concludes that the labs never built proper containment, and that perfect isolation is impractical for an agent that's meant to be useful.

- **What a sandbox walls off:** the filesystem and network.
- **What leaks anyway:** whatever the agents share, such as package caches, mounted volumes and git remotes.
- **The worm:** the agent doesn't need to be malicious. An obedient agent reads the planted instructions and carries them into the next sandbox.

It's the "one token wide" thread from AA15 one level down: the attack surface is now the plumbing between sandboxes, not the sandbox itself. What does your sandbox actually share, and would you know if something was left in it? — [Matthew Green](https://blog.cryptographyengineering.com/2026/09/30/is-sandboxing-sufficient-to-contain-rogue-agents/) — [Simon](https://simonwillison.net/2026/Oct/1/matthew-green/)

### Chirp Pong

Simon built a two-phone pong game in Claude Code on Opus 5.5, and the two phones talk to each other entirely through sound. The ball leaves one screen and arrives on the other because one phone chirps and the other listens.

- **Data over sound:** game state is encoded as short audio tones, played through one phone's speaker and decoded from the other's microphone.
- **It's the modem trick.** The idea is older than wifi. What's new is how little effort it took.
- **Built with:** Claude Code and Opus 5.5.

The point isn't pong. It's that a weekend joke project that once needed a signal-processing textbook now takes an afternoon of prompting. What's the most ridiculous thing you've shipped because it was suddenly cheap enough to try? — [Simon](https://simonwillison.net/2026/Oct/15/chirp-pong/)
